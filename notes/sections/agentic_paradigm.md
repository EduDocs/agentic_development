## Key points / spine
- **Agent = $(M,T,C,L)$** — model, tools, context, loop — running a perceive–reason–act cycle until a terminal condition. (Uniform non-calligraphic notation, settled 2026-07-12.)
- Tool set $T$ bounds what the agent *can* do; model $M$ decides what it *chooses* to do. Context is not persistent: what the model does not read, it does not know.
- **Capability ladder** (Operate → Build → Orchestrate → Evolve): each rung is a strict prerequisite for the next — "cannot evolve what you cannot evaluate." As tooling eases each rung's *mechanics*, the Operate paragraph escalates the *judgment* the tooling never carries: git-timing → build/architecture for discovery → the summit (which questions are worth pursuing, what counts as a meaningful contribution, what the results imply).
- **Two spines** introduced here and paid off at the capstone: Spine 1 *Evaluation Becomes Fitness* (Principle~EvalFitness: a *reusable validation* harness can serve as fitness — but not *any* harness: automatic, leakage-resistant, cheap/stable under repeated query, and distinct from a held-back final-test split); Spine 2 *Context Engineering* (the LLM is a function of its context; evolution is context engineering in a loop).
- **Why now**: instruction following + tool use + structured output combine to make an LLM a directable, composable, evaluable research substrate.
- **Workflow vs agent** (added handle): a *workflow* runs the model through predetermined code paths; an *agent* lets the model direct its own loop and tools — prefer a workflow unless the step count is genuinely open-ended (`figure:WorkflowAgentSpectrum`). Spine-1 nuance: a fixed evaluation decays as capability rises (temporal Goodhart → benchmark saturation, Ch.6), so fitness is an evolving artifact, not a fixed target.
- **Spine-1 evaluability spectrum**: the automatic score runs from *verifiable* problems (an unambiguous oracle: sphere-packing density, tests passing, model error) to problems of *judgment* (no formula; a capable model is the *critic* against a rubric: proof soundness at the frontier, prose, an idea's promise). Which end a task sits on is a property of the problem, not a preference. Verifiable end = cleanest for eval-becomes-fitness and where automated search has reached furthest; judgment end = softer/more gameable, but increasingly usable as models improve. Developed in the Evaluation chapter.
- **Spine-2 three-level progression**: the context lever has matured through *prompting* (2023: which question, how phrased) → *context engineering* (large windows/persistent profiles: what to put where, when to cache, when to clear) → *agentic context engineering* (the agent, on your machine, assembles its own context — which motivates giving it your files/tools/knowledge). The "agentic" adjective is deliberate. Detailed in the Rig and Context-Engineering chapters.
- **Build-time vs run-time** (Remark 2.4 close): the workflow↔agent choice is about the artifact that *runs*; agentic *development* is a build-time practice whose product is frequently a deterministic workflow or ordinary code with no agent in it. Developing *with* an agent ≠ deploying one; a central aim of the notes is to use agentic development to build reliable, largely non-agentic research pipelines.
