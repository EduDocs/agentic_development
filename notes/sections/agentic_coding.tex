\chapter{Agentic Coding}
\label{chapter:AgenticCoding}
% EVOLVE-BLOCK-START

Agentic coding is the practice of directing an AI agent to write, run, and revise code on your behalf.\index{Agentic!coding}
It is not passive: the researcher is not a bystander watching the agent write a program.
The researcher is the author who has contracted out the typing.
Every file the agent creates, every function it writes, every import it adds belongs to the researcher and will be submitted, graded, and eventually run again on a clean machine.

This distinction matters because agentic tools can produce large volumes of plausible-looking code very quickly.
The risk is not that the agent writes bad code; it is that the researcher stops reading.
The moment the researcher outsources \emph{comprehension} to the agent, the work ceases to be reproducible, auditable, or defensible.
Code ownership is key.
A practical test of it: if a collaborator, a reviewer, or a thesis committee asked why a particular line is there, could you answer without replaying the session that produced it?

Section~\ref{section:AgenticCodingLoop} lays out the read--direct--inspect loop; the sections that follow sharpen each phase in turn: directing the agent with precise instructions, reading the diff it produces (Section~\ref{section:ReadingDiff}), pinning a reproducible environment (Section~\ref{section:ReproducibleEnvironments}), and keeping a clean version history so the work stays auditable.

\section{The Agentic Coding Loop}
\label{section:AgenticCodingLoop}

Agentic coding proceeds in a cycle that alternates between researcher direction and agent execution.\index{Agentic!coding loop}

\begin{enumerate}
\item \textbf{Specify.} State clearly what the agent should produce (a function, a script, a test) with explicit constraints on interface, style, and correctness criteria.
\item \textbf{Execute.} The agent writes the code, runs it if appropriate, and reports the result.
\item \textbf{Read.} The researcher reads changes the agent made through diffs, file inspection, and testing.
\item \textbf{Commit or revise.} When the change is appropriate and understood, commit it. If not, provide corrective direction and iterate through the loop.
\end{enumerate}

One word in that list carries technical weight worth pinning down before the loop can be run.
To \emph{commit}\index{Commit} is to record the project's current state in its version history, along with a short note saying what changed and why.
A commit is not a backup of a file: it is a labelled point the project can be returned to, compared against, or undone back to, and it is what turns a session of edits into a record someone else can audit.

This iterative process is deliberately incremental.
Each cycle should produce a small, reviewable change, not a thousand-line scaffolding dump.
A change the researcher cannot fully read is a change the researcher does not own.

What makes the execute step more than fast code generation is the \emph{verification oracle}\index{Verification oracle}: the interpreter, test runner, or compiler the agent can invoke on its own output.
Each of those is a program that answers a question the agent cannot settle by reasoning alone.
The Python interpreter answers ``does this run at all'';
a \emph{test}\index{Test} is a small piece of code that calls your code on an input whose correct answer is already known and reports whether the two agree,
and a test runner is the program that executes every such check and tallies the failures.
In a chat interface, ``this code runs'' is a prediction.
In an agentic rig, it is a checked fact, and a failure returns a structured error signal (the line number, the type mismatch, the stack trace) that tells the agent exactly which assumption was violated.
A stack trace is simply the interpreter's report of where execution stopped and through which chain of calls it got there, which is why an agent can often repair a crash it did not anticipate.
This is why the loop converges even when the first attempt is wrong: each run--fail--fix cycle is grounded feedback, denser and more reliable than any specification the researcher could have written up front.
The same oracle, formalized as a scoring function, becomes the evaluation harness of Chapter~\ref{chapter:Evaluation}.

\begin{remark}
The oracle is not only the compiler, and it is not always binary.
The same loop serves a biochemist segmenting cells in microscopy images or an immunologist normalizing a flow-cytometry assay; only the check changes register.
That the script \emph{runs} is still the first oracle, necessary and cheap, but it cannot tell you whether the analysis is \emph{right}.
For that, the data-science counterpart of the test suite is a \emph{known test set}: a few images with hand-annotated counts, or a control sample of known concentration, on which the output is scored against ground truth (a segmentation overlap, a recovered parameter, a classification error).
This oracle is graded rather than pass/fail, yet it is still an oracle: it returns a number the loop can act on.
Softer still is whether the \emph{workflow suits the problem} at all: whether simple thresholding fits unevenly stained images, or whether a linear model belongs on a plainly sigmoidal dose--response.
That is a matter of judgment, not a test: it sits at the \emph{critic} end of the evaluability spectrum (Chapter~\ref{chapter:AgenticParadigm}, developed in Chapter~\ref{chapter:Evaluation}), and it is exactly the discernment the researcher must keep.
\end{remark}

\begin{principle}
\label{principle:IncrementalDevelopment}
Prefer small, reviewable changes over large, opaque ones.
An instruction that says ``implement the entire pipeline'' will produce code faster than ``implement the data loader, then stop'' — but the former is harder to verify and harder to correct.
Small steps compound correctly; large steps compound errors.
\end{principle}

\section{Directing the Agent Effectively}

The quality of an agent's code output is strongly predicted by the quality of the researcher's direction.
Vague instructions produce vague implementations; incomplete specifications produce code that solves the wrong problem.

\subsection{Specify the Interface First}

Before asking the agent to implement a function, state its interface: name, parameters, return type, and any invariants.
The \emph{interface} is everything a caller needs to know in order to use the function without reading its body, and an \emph{invariant} is a property that must hold on every call: that the returned value is never negative, that two arrays have matching lengths, that the input is left unmodified.
A well-specified interface constrains the implementation space and makes correctness easier to verify.
What it buys is a contract fixed before any code exists: with the interface written down, the researcher can say whether an implementation is right without first reconstructing what was intended.

\begin{example}
A poor specification:
\begin{lstlisting}[language=python]
# "write a function to score a model"
\end{lstlisting}
A good specification:
\begin{lstlisting}[language=python]
def score(model, X_test, y_test):
    """Return mean squared error of model.predict(X_test) vs y_test.
    Both X_test and y_test are numpy arrays.
    The return value is a non-negative float.
    Raise ValueError if arrays have incompatible shapes."""
\end{lstlisting}
The second version is not code the researcher had to write: it is a signature and a docstring, handed to the agent \emph{as} the instruction, with the body left for the agent to fill in.
Notice that it pins four separate things: what is computed, what the inputs are, what the output looks like, and what should happen when the inputs are malformed.
The second version leaves far less room to misunderstand the task; a precise interface constrains ambiguity, though it cannot rule out semantic misunderstanding entirely.
\end{example}

\subsection{Cite the Files That Matter}

When the implementation must interact with existing code, name the files explicitly.
``Extend the loader to support CSV files'' is less precise than ``modify \code{src/loader.py}, specifically the \code{load\_dataset} function, to accept files with a \code{.csv} extension as well as \code{.npz}.''
The notation \code{src/loader.py} is a path: it names the file \code{loader.py} inside the folder \code{src} inside the project, and it is how one refers to a file unambiguously when a project holds dozens of them.
The agent may otherwise modify a different file, or write new code that duplicates existing functionality.
This is a common and expensive failure: the project ends up with two loaders that disagree, and the one being tested is not the one being run.

\subsection{One Task per Instruction}

Compound instructions that ask for several things at once produce compound diffs that are harder to review and harder to revert if one part is wrong.

\begin{remark}
``Add a CSV loader, write tests for it, and update the \code{CLAUDE.md} to document it'' is three tasks.
If the tests are wrong, reverting them also reverts the loader.
Three separate instructions (e.g., loader, then tests, then documentation) each produce a single-purpose commit that can be independently reviewed, accepted, or reverted.
\end{remark}

\section{Reading the Diff}
\label{section:ReadingDiff}

A \emph{diff}\index{Diff} is a compact representation of the changes between two versions of a file: lines added are prefixed with~\code{+}; lines removed with~\code{-}.
Reading diffs before committing is a cornerstone habit in agentic coding.

\begin{example}
A minimal diff showing the addition of a CSV branch to a loader:
\begin{lstlisting}[language=diff]
--- a/src/loader.py
+++ b/src/loader.py
@@ -12,6 +12,10 @@ def load_dataset(path):
     if path.endswith('.npz'):
         data = np.load(path)
         return data['X'], data['y']
+    elif path.endswith('.csv'):
+        df = pd.read_csv(path)
+        X = df.drop(columns=['target']).values
+        y = df['target'].values
+        return X, y
     raise ValueError(f"Unsupported format: {path}")
\end{lstlisting}
The layout is worth decoding once, since every diff a reader will ever see shares it.
The first two lines name the file as it was (\code{a/}) and as it now is (\code{b/});
the line beginning \code{@@} locates the excerpt, reporting where in the file the shown region starts and how long it is before and after the change.
Lines beginning with a space are unchanged context, printed only so the reader can see where the new lines land,
and the text after the closing \code{@@} names the enclosing function.
A diff therefore shows a neighborhood, not a whole file: it is meant to be read in full in seconds, which is what makes reading every one of them a realistic habit rather than a pious one.
Reading this diff reveals that the CSV branch assumes the target column is named \code{'target'} and that the remaining columns are all features.
Neither of these constraints appears in the instruction; both affect correctness on real data.
The diff also introduces a dependency on \code{pandas} (the \code{pd} alias) that must already be present in the environment, itself a change worth catching in the diff rather than at run time on a clean machine.
\end{example}

\begin{example}
Consequential changes are not always large ones.
Asked to make the loader robust to malformed input, an agent might change a single line:
\begin{lstlisting}[language=diff]
-        df = pd.read_csv(path)
+        df = pd.read_csv(path).dropna()
\end{lstlisting}
The code runs, the shapes printed to the screen look reasonable, and any test that only checks the loader returns two arrays still passes.
What changed is the sample: every row holding a single missing measurement is now silently discarded.
An economist loses the households that skipped one survey question, an ecologist loses the sites with one unread sensor, and in both cases the remaining rows are no longer a random subset.
Nothing downstream announces this, and no oracle in the loop is asking the question.
The diff is the only place the change is visible before the results are written up.
\end{example}

Reading diffs develops two habits.
The first is \emph{catching errors}: agents make mistakes --- wrong assumptions, missing edge cases, subtle logic errors --- that are invisible in the running output but legible in the diff.
The second is \emph{maintaining ownership}: a researcher who reads every diff understands their own codebase; one who does not is dependent on the agent to remember what was done and why.

\begin{remark}
The  habit of reading changes and owning the result is what Anthropic's AI-fluency framework names \emph{diligence}: the discipline of ensuring that the speed an agent offers never costs the researcher responsibility, transparency, or accountability for what remains their own work.
Its companion competences in that framework, \emph{description} and \emph{discernment}, are developed in Chapter~\ref{chapter:ContextEngineering} and Chapter~\ref{chapter:Evaluation}.
\end{remark}

\section{Reproducible Environments}
\label{section:ReproducibleEnvironments}

A piece of code is reproducible when anyone can clone the repository, follow the documented procedure, and obtain the same result.\index{Reproducible environment}
To \emph{clone} a repository is to copy the project, with its full history, onto another machine; the phrase stands in for the realistic case in which a collaborator, a referee, or the researcher a year from now begins with nothing but the repository and a computer that has never run this code.
For Python projects, reproducibility requires that the exact versions of all dependencies be recorded and restorable.
The failure this guards against is mundane: an analysis works on your laptop because you happened to install a library there two years ago, and the repository never says so, so it works nowhere else.

\subsection{Dependency Pinning}

A \emph{pinned dependency}\index{Dependency pinning} specifies an exact package version, not a version range.
Both files below are plain text, live at the top of the project, and are read by the installer; the \code{==} is the pin, meaning ``this version and no other.''

\begin{example}
A loosely specified dependency and its pinned equivalent:
\begin{lstlisting}[language=toml]
# pyproject.toml — imprecise
[project]
dependencies = ["numpy", "scikit-learn"]

# requirements.txt — pinned
numpy==2.1.3
scikit-learn==1.6.1
scipy==1.14.1
\end{lstlisting}
Notice that the pinned list contains \code{scipy}, which nobody asked for: it arrives because \code{scikit-learn} depends on it, and pinning what your dependencies themselves depend on is what makes the environment reconstructable rather than merely described.
The loose specification allows a collaborator to install a different version than the author used, potentially changing numerical results.
A changed default solver or a reseeded random-number stream between two minor releases is enough to move a fitted coefficient, and two runs of the same analysis then disagree for reasons no one can see in the code.
The pinned specification pins the Python package versions, a necessary step toward reproducibility, though not by itself a guarantee of an identical environment.
\end{example}

\begin{remark}
Pinning dependencies is necessary but not sufficient.
An Anthropic engineering postmortem (2025) documents that identical model weights can produce different outputs depending on the serving stack (routing, hardware, compiler flags) so recording the model \emph{name} does not by itself pin the model; when a pipeline calls a hosted model, log the served endpoint and version too.
And when the environment is a resource-bounded container, the resource budget is itself a variable: raising CPU or memory ceilings can change which solution strategies an agent can even reach, so a reproducible run pins resource floors and ceilings alongside dependency versions.
\end{remark}

\subsection{Virtual Environments}

A \emph{virtual environment}\index{Virtual environment} is an isolated Python installation that contains only the packages a specific project requires.
This prevents conflicts between projects that require different versions of the same package and ensures that the installed packages are exactly the ones listed in the requirements file.

\begin{lstlisting}[language=bash]
python -m venv .venv               # create a virtual environment
source .venv/bin/activate          # activate it (macOS / Linux)
pip install -r requirements.txt    # install pinned dependencies
\end{lstlisting}

The three commands do three different things.
The first creates a folder named \code{.venv} inside the project holding a private copy of Python;
the second rewires the terminal session so that \code{python} and \code{pip} refer to that copy instead of the machine-wide one;
the third installs the pinned versions into it.
Activation lasts only for that terminal window, which is why a freshly opened terminal must activate again before the project's packages are visible: a great deal of early confusion is nothing more than a forgotten activation.

Modern projects often use tools like \code{uv} or \code{poetry} to manage virtual environments and pin dependencies automatically.

\subsection{One-Command Run}

The final requirement for reproducibility is a single command that installs dependencies, loads data, runs the pipeline, and reports the result with no manual steps in between.

\begin{example}
Using \code{just} as a command runner:
\begin{lstlisting}[language=bash]
# justfile
run:
    uv run python -m challenge1

# the researcher (or evaluator) runs:
just run
\end{lstlisting}
A \code{justfile} is a plain text file at the top of the project listing named recipes; \code{just run} looks up the recipe called \code{run} and executes the commands underneath it.
The point is not the tool but the relocation of knowledge: the exact invocation is written down once by the author rather than reconstructed by every reader from a paragraph of prose in a README.
If an evaluator cannot reproduce the result with one command, the work is not reproducible.
\end{example}

\section{Clean Version History}

A clean version history is one where each commit has a single purpose, a clear message, and represents a state the project can return to.
An agent that is given broad latitude will often produce long sessions of changes; the researcher's job is to organize those changes into coherent commits.

\subsection{Atomic Commits}

An \emph{atomic commit}\index{Atomic commit} is a commit that contains exactly one conceptual change.
Atomic commits make the history navigable: each commit can be understood, reverted, or cherry-picked independently.
To \emph{revert} a commit is to undo exactly that change while keeping everything committed after it; to \emph{cherry-pick} one is to copy that change, and only that change, onto a different line of work.
Both operations are only as sharp as the commits allow, because neither can extract half of a commit: this is the whole practical argument for keeping them atomic.
A cohesive change and the tests that verify it are one conceptual change, not two: splitting an implementation from its tests leaves commits that do not pass on their own, so the aim is a commit that is coherent, tested, and independently reviewable rather than merely small.

\begin{principle}
\label{principle:AtomicCommits}
Before committing, ask: ``If I need to undo \emph{just this one thing}, can I?''
If the answer is no — because the commit combines two unrelated changes — split it.
A commit history is a journal; each entry should have exactly one topic.
\end{principle}

\subsection{Commit Messages}

A commit message should describe \emph{why} the change was made, not just what changed (the diff already shows what changed).

\begin{example}
Uninformative and informative commit messages for the same change:
\begin{lstlisting}[language=bash]
# poor
git commit -m "fix bug"

# better
git commit -m "Score on validation split, not full dataset (was leaking into fitness)"
\end{lstlisting}
The bug it names is a leak: the model was being scored on data it had already been fitted to, which inflates the score and makes a weak model look strong.
The second message names the bug and explains why it matters.
Six months later, the author will be grateful for it, and so will anyone auditing which reported numbers were affected.
\end{example}
